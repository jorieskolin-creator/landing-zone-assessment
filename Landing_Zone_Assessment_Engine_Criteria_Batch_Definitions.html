Landing Zone Assessment Engine — Criteria & Batch Definitions

One product. Eight design-area batches. Each batch holds five capabilities paired against five anti-patterns. Each criterion carries three shared sub-criteria — the questions the auditor and the workshop must pass. Azure, AWS and Google Cloud do not get three separate catalogues. They get provider packs inside the Engine: the same intent ID, the same pair, different control-plane evidence.

01How the Engine divides work

Canonical intent is the index. Provider criteria are what get scored.

The Engine cannot separate Azure from AWS from GCP unless those checks live in the domain pack. The workshop does not fork. The pack does.

Layer 1

Design area

Batches A–H. Same taxonomy on every cloud. Same radar, same quality gate, same report spine.

Layer 2

Intent + pair

Capability B2 pairs with anti-pattern AP-B2. Shared ID. Shared 3 questions. Shared scoring math.

Layer 3

Workshop themes

Three facilitator questions per batch. One script. Interviews explain; they do not replace inventory.

Layer 4 · Engine content

Provider packs

Azure / AWS / GCP evidence contracts, object names, tested-absence queries. This is what Phase 1 scores.

Mapped

Same intent, different objects. Most rows in this catalogue. Example: time-bound privilege → PIM / Identity Center / PAM.

Native

Exists on one cloud. Keep it. Do not invent a fake twin. Mark the others not applicable, not zero.

Not applicable

Cloud out of Step 0 scope, or no equivalent object. Silent. Unknown is not Crawl.

If a provider check is not in the pack, the Engine cannot assess it. Silence is data. It is not a 0.

02Record shape

What is actually stored in the Engine

One criterion record. Provider is a field, not a product fork. Step 0 loads only the packs in scope. 

{
  "id": "B2",
  "intentId": "privileged-access-timebound",
  "designArea": "identity",
  "stream": "capability",
  "pair": "AP-B2",
  "statement": "Privileged access is eligible, time-bound and logged.",
  "subcriteria": [
    "Are privileged roles eligible rather than permanently assigned to humans?",
    "Is activation time-bound, approved or justified, and written to an audit log?",
    "Is standing owner-equivalent access on humans treated as an exception with an expiry?"
  ],
  "providers": {
    "azure": {
      "kind": "mapped",
      "evidence": ["pim-policy", "role-assignment", "activation-log"]
    },
    "aws": {
      "kind": "mapped",
      "evidence": ["identity-center-permission-set", "iam-user-admin", "cloudtrail"]
    },
    "gcp": {
      "kind": "mapped",
      "evidence": ["iam-conditions", "pam", "org-iam"]
    }
  }
}

Runtime: if Step 0 scopes Azure + AWS, the GCP object is not evaluated and is not scored as zero. Multi-cloud roll-up stays named: “Azure identity GO, AWS identity WARN” — never a blended 3.2.

A
Tenant, billing & organization construct
5 capabilities · 5 anti-patterns · 30 shared sub-criteria · 3 provider packs

Workshop themes — one script for every cloud

  1. Where is the authoritative cloud organization, and who owns it?
  2. Are production workloads forbidden from the management/payer plane?
  3. Does billing, contract and technical ownership describe the same estate?
Stream A · Capabilities
A1 · authoritative-org-root · pair AP-A1
Authoritative organization root
A single declared tenant, organization or management account is the landing-zone root. Production resources do not live in unmanaged side-tenants. The root is inventoryable.
  1. Is there a single declared tenant, organization or management account that is the landing-zone root?
  2. Can that root be exported as a hierarchy (management groups, OUs or folders) with a named owner?
  3. Are production workloads forbidden from existing outside that root?
Azure
Entra tenant ID, Tenant Root Group, MCA/EA billing account attached to the tenant.
AWS
Organizations management account, Root, ALL_FEATURES enabled; no extra orgs holding prod accounts.
GCP
Organization resource + Cloud Identity; billing account linked to the org, not to a lone project.
A2 · management-plane-hygiene · pair AP-A2
Management-plane hygiene
The management, payer or bootstrap plane runs only organization services. Application workloads, data and developer sandboxes are not hosted there.
  1. Is the management, payer or bootstrap account free of application workloads?
  2. Are only organization-level services (identity, logging, policy, connectivity) deployed there?
  3. Is access to that plane separately controlled and reviewed?
Azure
No app resource groups in Management / Identity / Connectivity platform subscriptions beyond platform services.
AWS
Organizations management account has no application VPCs, data stores or IAM users for app teams.
GCP
No application folders or projects under the bootstrap/seed project; org-level services only.
A3 · billing-contract-alignment · pair AP-A3
Billing and contract alignment
Commercial construct (EA/MCA, payer, billing account) matches the technical organization. Cost, invoice and account ownership can be named.
  1. Is the billing account, payer or enrollment mapped to the same organization as the technical hierarchy?
  2. Can every in-scope subscription, account or project be attributed to a billing owner?
  3. Are orphaned billing scopes (unused enrollments, extra payers) identified and closed or explicitly out of scope?
Azure
MCA/EA billing account, billing profiles, invoice sections vs management group tree.
AWS
Consolidated billing, payer account, linked accounts; AWS Organizations vs Billing Conductor if used.
GCP
Cloud Billing account, org-level billing export, projects billed outside the org.
A4 · administrative-boundary · pair AP-A4
Administrative boundary clarity
Partner, guest, sandbox and merged-company tenants are named. The assessment scope is a declared set of roots, not 'whatever we found'.
  1. Are partner, guest, sandbox and acquisition tenants explicitly in-scope or out-of-scope?
  2. Is there an inventory of extra directories, organizations or billing accounts?
  3. Does Step 0 lock the in-scope roots before scoring begins?
Azure
Extra Entra tenants, B2B guest tenants, Azure DevOps orgs, unused EA enrollments.
AWS
Standalone accounts outside the org, extra Organizations, AWS Gov/China partitions if present.
GCP
Projects with no parent org, extra Google Workspace domains, unmanaged GCP folders.
A5 · root-recovery · pair AP-A5
Root recovery and emergency access
Loss of the cloud-root identity does not mean loss of the estate. Emergency access is designed, stored, tested and monitored — not a password in a ticket.
  1. Is there a documented emergency-access path to the tenant, management account or org super-admin?
  2. Is that path stored offline or in a vault, with dual control, and tested on a cadence?
  3. Are root/emergency authentications logged and alerted?
Azure
Break-glass Entra cloud-only accounts, PIM for Global Admin, emergency access package.
AWS
Root MFA, hardware key, no root access keys; Organizations delegated admin; Account Recovery.
GCP
Super-admin dual control, recovery email/phone, organization-admin not bound to one human.
Stream B · Anti-patterns
AP-A1 · shadow-tenants · pair A1
Shadow tenants and unmanaged orgs
Production lives in extra directories, organizations or personal accounts that the platform team cannot inventory or govern.
  1. Do production workloads exist in tenants, organizations or accounts outside the declared root?
  2. Is there no maintained inventory of extra directories or billing relationships?
  3. Are mergers, partners or 'temporary' clouds still running production without a landing-zone owner?
Azure
Second Entra tenant with subscriptions; MSDN / personal tenants used for prod.
AWS
Member accounts not in the org; root-less standalone prod accounts.
GCP
No-organization projects; billing on a user account.
AP-A2 · workloads-in-management-plane · pair A2
Workloads in the management plane
Applications, data lakes or developer sandboxes sit in the management, payer or tenant-root subscription. A landing-zone change now risks the company.
  1. Are application resources deployed in the management, payer or bootstrap account?
  2. Would a landing-zone rebuild require migrating production out of that plane first?
  3. Do app teams have standing contributor rights on the management plane?
Azure
App resource groups in the Management or Tenant Root subscription.
AWS
Application VPCs, S3 data or RDS in the Organizations management account.
GCP
App GKE or data projects under the seed/bootstrap project.
AP-A3 · billing-split-from-tech · pair A3
Billing split from technical ownership
Finance pays a bill that platform cannot map. Technical owners cannot name the contract. Scope debates replace assessment.
  1. Can platform and finance not agree which subscriptions, accounts or projects are in-scope?
  2. Are invoices received for clouds that have no landing-zone owner?
  3. Is cost allocation blocked because billing structure does not match the hierarchy?
Azure
EA enrollment not matching management groups; Azure Plan vs tenant mismatch.
AWS
Payer account in a different org; linked accounts billed but not in Organizations.
GCP
Billing account owned by a user; projects billed outside the org.
AP-A4 · unbounded-guest-root · pair A4
Unbounded guest or partner access at root
External identities hold owner-equivalent rights at tenant, organization or management-account level with no expiry.
  1. Do guest, partner or vendor identities hold owner-equivalent roles at the root?
  2. Is that access standing (no expiry, no dual control)?
  3. Is there no review of external admin at the organization plane?
Azure
Guest Global Admin or Owner at Tenant Root Group.
AWS
External IAM or assumed roles with AdministratorAccess on the management account.
GCP
External users with roles/resourcemanager.organizationAdmin.
AP-A5 · unowned-root-credentials · pair A5
Unowned root credentials
Root, super-admin or Global Admin credentials are shared, unlogged, or known only to a departed person.
  1. Are root or super-admin credentials shared, stored in email, or unused-and-unknown?
  2. Is there no MFA or hardware key on the cloud root?
  3. Would the estate be unrecoverable if one person left?
Azure
Shared Global Admin password; no break-glass; no PIM.
AWS
Root access keys exist; root MFA unset; root used as a daily login.
GCP
Single super-admin; recovery options stale; no 2-step verification.
B
Identity & access
5 capabilities · 5 anti-patterns · 30 shared sub-criteria · 3 provider packs

Workshop themes — one script for every cloud

  1. How does a human get access, and how is it taken away?
  2. How is privileged access made eligible, time-bound and logged?
  3. How do workloads authenticate without long-lived secrets?
Stream A · Capabilities
B1 · federated-workforce-identity · pair AP-B1
Federated workforce identity
Workforce access uses the corporate identity provider. Cloud-local users are not the primary human identity. Joiners, movers and leavers follow the IdP.
  1. Is workforce sign-in federated from the corporate identity provider to every in-scope cloud?
  2. Are cloud-local human users the exception, inventoried, and expiry-bound?
  3. Does leaver processing in the IdP actually remove cloud access?
Azure
Entra ID / AD FS federation; cloud-only users listed and justified.
AWS
IAM Identity Center (SSO) to the IdP; IAM users for humans are exceptions.
GCP
Cloud Identity / Workforce Identity Federation; no standing Google user as org admin for staff.
B2 · privileged-access-timebound · pair AP-B2
Time-bound privileged access
Privileged roles are eligible, activated, time-bound and logged. Standing Global Admin, AdministratorAccess or organizationAdmin for humans is not the operating model.
  1. Are privileged roles eligible rather than permanently assigned to humans?
  2. Is activation time-bound, approved or justified, and written to an audit log?
  3. Is standing owner-equivalent access on humans treated as an exception with an expiry?
Azure
Entra PIM eligible roles, activation logs, Access Reviews.
AWS
Identity Center permission sets, session duration, CloudTrail; no standing AdministratorAccess on humans.
GCP
PAM / IAM Conditions / time-bound grants; no standing roles/owner on users at org root.
B3 · workload-identity · pair AP-B3
Workload identity without long-lived keys
Compute, pipelines and services authenticate with federated or managed identities. Long-lived access keys and downloaded JSON keys are not the default.
  1. Do platform and application workloads use managed or federated identities rather than stored keys?
  2. Are remaining long-lived keys inventoried, aged, and on a removal path?
  3. Do CI/CD platforms federate into the cloud rather than store cloud secrets?
Azure
Managed identities, workload identity federation (GitHub/ADO), no client secrets in pipelines.
AWS
IRSA / instance profiles / IAM Roles Anywhere; IAM user access keys for workloads absent or aged.
GCP
Attached service accounts, Workload Identity Federation; no downloaded JSON keys for automation.
B4 · least-privilege-inheritance · pair AP-B4
Least-privilege inheritance
Role assignment follows the hierarchy. Owner-equivalent at tenant, org or management-group root is rare, named, and not used for daily work.
  1. Are role assignments scoped to the landing zone or workload, not the organization root, by default?
  2. Is Owner / AdministratorAccess / roles/owner at root limited to a break-glass set?
  3. Can the platform show who has owner-equivalent rights, where, and why?
Azure
MG/subscription/RG RBAC; Owner at Tenant Root Group listed; custom roles over Owner.
AWS
SCPs + Identity Center permission sets by OU; IAM policies not attached at org root for humans.
GCP
Folder/project IAM; organization-level roles/owner and editor listed and justified.
B5 · break-glass-monitored · pair AP-B5
Monitored break-glass
Emergency access exists, is dual-controlled, is unused in daily operations, and fires a detection when used.
  1. Do named break-glass identities exist, with dual control, outside normal federation failure modes?
  2. Are they excluded from daily use by policy and culture?
  3. Does use generate a high-severity alert within minutes?
Azure
Cloud-only break-glass accounts, excluded from PIM but alerted via Entra / Sentinel.
AWS
Break-glass IAM role or root procedure; CloudTrail + GuardDuty / EventBridge alert on use.
GCP
Break-glass super-admin or PAM emergency grant; Cloud Audit Logs alert.
Stream B · Anti-patterns
AP-B1 · standing-root-equivalent · pair B1
Standing root-equivalent access
Humans hold permanent Global Admin, AdministratorAccess or organizationAdmin. Privilege is a lifestyle, not an event.
  1. Do humans hold standing owner-equivalent roles at tenant, org or account root?
  2. Is there no activation, time-bound or approval step?
  3. Is that population larger than a named break-glass set?
Azure
Permanent Global Admin or Owner at Tenant Root Group.
AWS
IAM users or SSO groups with AdministratorAccess on the management account, standing.
GCP
Users with roles/owner or organizationAdmin at org, standing.
AP-B2 · local-cloud-users · pair B2
Local cloud users as primary identity
People log in with cloud-native users disconnected from the corporate IdP. Leavers keep access. Joiners get a second identity to babysit.
  1. Are cloud-local human users the normal way to access the estate?
  2. Does leaver processing in the corporate IdP leave cloud access intact?
  3. Are shared logins (team@, admin@) in use?
Azure
Cloud-only Entra users for staff; shared admin mailboxes.
AWS
IAM users with passwords/keys as the daily path; unused Identity Center.
GCP
Consumer Gmail or unmanaged Google users on org IAM.
AP-B3 · long-lived-keys-as-identity · pair B3
Long-lived keys as identity
Access keys, client secrets and downloaded service-account keys are how automation and people authenticate. Rotation is a wish.
  1. Are long-lived access keys or JSON service-account keys the default for workloads or humans?
  2. Are keys older than policy (or unaged) still valid?
  3. Do pipelines store cloud credentials in variables rather than federate?
Azure
SP client secrets in ADO/GitHub; unused managed identity.
AWS
IAM user access keys for CI and humans; keys never rotated.
GCP
Downloaded SA JSON keys in repos or Secret Manager used as identity.
AP-B4 · unscoped-owner-at-root · pair B4
Unscoped Owner at root
Application teams receive Owner, Editor or AdministratorAccess at the organization or management-group root 'so they can work'. Guardrails cannot hold.
  1. Do application teams hold owner-equivalent rights at the organization or management-group root?
  2. Can they disable policy, networking or logging as a side effect of that grant?
  3. Is there no alternative scoped role for daily delivery?
Azure
App groups assigned Owner at Tenant Root or intermediate MG.
AWS
Dev SSO group with AdministratorAccess on * or on the root OU.
GCP
App groups with roles/editor or owner on the organization.
AP-B5 · unmonitored-break-glass · pair B5
Unmonitored or missing break-glass
Either emergency access does not exist, or it exists and nobody would notice if it were used — or abused.
  1. Is there no designed emergency-access path?
  2. Is emergency access used as a daily convenience account?
  3. Would use of emergency access produce no alert?
Azure
No break-glass; or Global Admin shared and unalerted.
AWS
Root used as a shared login; no CloudTrail alarm on root.
GCP
Super-admin used daily; no audit-log alert.
C
Resource organization
5 capabilities · 5 anti-patterns · 30 shared sub-criteria · 3 provider packs

Workshop themes — one script for every cloud

  1. Does the hierarchy encode policy, or is it a filing cabinet?
  2. Where does the platform landing zone end and an application landing zone begin?
  3. How is a new subscription, account or project born?
Stream A · Capabilities
C1 · hierarchy-encodes-policy · pair AP-C1
Hierarchy that encodes policy
Management groups, OUs or folders are the policy inheritance spine. Placement of a workload decides its guardrails, not a wiki page.
  1. Does every in-scope subscription, account or project sit under a designed hierarchy node?
  2. Is policy inherited from those nodes rather than applied one-by-one as a hobby?
  3. Can the platform explain what moving a workload to another node would change?
Azure
Management group tree from Tenant Root; Azure Policy assignments at MG.
AWS
OU tree; SCPs attached to OUs, not only to individual accounts.
GCP
Folder tree; Organization Policy on org/folders, not only on projects.
C2 · platform-vs-app-lz · pair AP-C2
Platform versus application landing zones
Identity, connectivity, management and security sit in platform landing zones. Applications sit in application landing zones that consume those services.
  1. Are platform services (identity, hub network, logging, security) separated from application workloads?
  2. Do application landing zones consume shared services rather than rebuild them?
  3. Is ownership of platform vs application landing zones named?
Azure
CAF platform MGs/subscriptions (Identity, Connectivity, Management) vs Corp/Online app MGs.
AWS
Log Archive, Audit, Network, Identity accounts vs workload OUs (Control Tower / custom).
GCP
Bootstrap, logging, networking, security folders vs application folders.
C3 · naming-tagging-enforced · pair AP-C3
Naming and tagging enforced
A naming and tagging standard exists, is machine-enforced at vending time, and untagged or illegally named resources are visible as exceptions.
  1. Is there a documented naming and tagging standard for subscriptions, accounts, projects and resources?
  2. Is it enforced at create-time (policy, SCP or vending pipeline), not only in a slide?
  3. Are violations tracked and remediated rather than accepted as noise?
Azure
Azure Policy required-tags; naming via Bicep/AVM or subscription vending.
AWS
SCP / Config / Tag Policies; Control Tower or AFT account naming.
GCP
Org policy, labels, project-id convention in the project factory.
C4 · governed-vending · pair AP-C4
Governed subscription / account / project vending
New isolation units are created by a pipeline or service catalog, with identity, network, policy and logging attached at birth — not by a portal click and a hope.
  1. Are new subscriptions, accounts or projects created through a vending path rather than ad-hoc portal clicks?
  2. Does the vended unit land in the correct hierarchy node with baseline policy, identity and logging?
  3. Can the platform show the last N vended units and their owners?
Azure
Subscription vending (Azure LZ accelerator, ALZ, service catalog).
AWS
Account Factory / AFT / custom Organizations pipeline.
GCP
Project factory (Terraform), Seed + CI; no ad-hoc console projects.
C5 · environment-separation · pair AP-C5
Environment separation
Production is a different landing-zone node from non-production. Blast radius, identity and data paths respect that line.
  1. Are production and non-production in distinct hierarchy nodes or landing zones?
  2. Can non-production identities not administer production by default?
  3. Is data-path isolation (network, identity, key) designed, not accidental?
Azure
Corp-prod vs Corp-nonprod MGs; separate subscriptions; no shared Owner group.
AWS
Prod vs SDLC OUs; SCPs differ; no shared admin permission set.
GCP
Prod vs nonprod folders; VPC-SC / IAM differ by folder.
Stream B · Anti-patterns
AP-C1 · flat-sprawl · pair C1
Flat subscription or account sprawl
Hundreds of subscriptions, accounts or projects hang off the root. Policy cannot inherit. Nobody can draw the map.
  1. Do most isolation units sit directly under the tenant, org root or a single catch-all node?
  2. Is the hierarchy unused as a policy spine?
  3. Can the platform not produce a current map of nodes and owners?
Azure
All subscriptions under Tenant Root Group.
AWS
All accounts in Root; empty OU design.
GCP
All projects directly under the organization.
AP-C2 · apps-in-platform · pair C2
Applications in the platform landing zone
Business systems share the connectivity, identity or management subscription. Platform change freezes the business; business change risks the platform.
  1. Do application workloads share platform subscriptions, accounts or projects?
  2. Would a platform rebuild collide with application data?
  3. Are application teams granted rights on platform landing zones to 'get things done'?
Azure
App resource groups in Connectivity or Management subscriptions.
AWS
Workload VPCs in the Network or Audit account.
GCP
App GKE in the shared-vpc host or logging project.
AP-C3 · adhoc-naming · pair C3
Ad-hoc naming and tag theatre
Names are local jokes. Tags exist in a PDF. Create-time enforcement is absent. Search, cost and incident response guess.
  1. Do names and tags differ by team with no enforced standard?
  2. Is the tagging standard documentation-only?
  3. Are untagged resources treated as acceptable?
Azure
No required-tag policy; subscription names like 'test2-final'.
AWS
No tag policies; account emails as the only identifier.
GCP
No label convention; project IDs are random or personal.
AP-C4 · clickops-birth · pair C4
ClickOps birth of isolation units
Subscriptions, accounts or projects are created in the portal, emailed into existence, or copied from a neighbour. Baseline is optional.
  1. Is the normal create path a portal click or a ticket to a human who clicks?
  2. Do new units appear without policy, logging or network baseline?
  3. Is there no record of who requested the unit and why?
Azure
Portal-created subscriptions not in the vending app.
AWS
Organizations 'Add account' by hand; no AFT/Control Tower.
GCP
Console 'create project' by developers.
AP-C5 · mixed-environments · pair C5
Mixed environments in one boundary
Production, test and playground share a subscription, account or folder. A playground identity can reach production data.
  1. Do production and non-production share the same isolation unit?
  2. Can non-production identities reach production data or keys?
  3. Is 'we use resource groups / VPCs instead' used to avoid a landing-zone line?
Azure
Prod and dev resource groups in one subscription with shared Owner.
AWS
Prod and sandbox in one account; one admin role.
GCP
Prod and playground in one project or shared folder IAM.
D
Network topology & connectivity
5 capabilities · 5 anti-patterns · 30 shared sub-criteria · 3 provider packs

Workshop themes — one script for every cloud

  1. Where is the hub, and what is forced through it?
  2. Who owns hybrid connectivity, DNS and inspection?
  3. Is private-by-default a control, or a preference?
Stream A · Capabilities
D1 · hub-with-inspection · pair AP-D1
Hub topology with inspection
A designed hub (hub-spoke, Virtual WAN, Transit Gateway, Shared VPC) exists. Spoke-to-spoke and egress paths are intentional. Inspection is a placement, not a hope.
  1. Is there a designed hub that spokes must use for shared and egress traffic?
  2. Are inspection points (firewall, IDS, web proxy) placed on those forced paths?
  3. Is spoke-to-spoke traffic an explicit pattern rather than a mesh accident?
Azure
Hub-spoke or vWAN; Azure Firewall / NVA; spoke peering without use-remote-gateway exceptions unlisted.
AWS
Transit Gateway / Cloud WAN; inspection VPC; no VPC-peering spaghetti as the primary pattern.
GCP
Shared VPC + hub; Cloud Firewall / NGFW; no project-level public default.
D2 · hybrid-connectivity-owned · pair AP-D2
Owned hybrid connectivity
ExpressRoute, Direct Connect, Interconnect, VPN and SD-WAN land in the platform, not in an application subscription. Ownership, redundancy and failover are named.
  1. Do hybrid circuits terminate in a platform connectivity landing zone?
  2. Are redundancy, failover and who-to-call documented and tested?
  3. Can application teams not create competing hybrid paths as a side door?
Azure
ExpressRoute / VPN Gateway in Connectivity subscription; no app-level ER circuits.
AWS
DX Gateway / VPN on the network account; TGW attachments governed.
GCP
Dedicated/Partner Interconnect on the host project; no per-app interconnects.
D3 · central-dns · pair AP-D3
Central DNS
Private DNS is a platform service. Resolution of on-premises, PaaS private endpoints and landing-zone names is consistent. Split-brain is a tracked exception.
  1. Is private DNS administered as a platform service rather than per application?
  2. Do private endpoints and hybrid names resolve consistently in every landing zone?
  3. Are rogue DNS forwarders inventoried?
Azure
Private DNS zones in Connectivity; Azure Policy for private-endpoint DNS; inbound/outbound resolvers.
AWS
Route 53 private hosted zones + Resolver rules in the network account.
GCP
Cloud DNS private zones on the host project; inbound/outbound forwarding.
D4 · private-by-default · pair AP-D4
Private-by-default
Public endpoints are denied or exception-gated. PaaS public access is off unless an expiry-bound exemption exists.
  1. Is public network access denied by policy for relevant services unless exempted?
  2. Are remaining public endpoints inventoried with owner and expiry?
  3. Is internet egress a controlled hub path rather than every NIC for itself?
Azure
Azure Policy deny public IP / public blob / public Key Vault; Firewall / NAT at hub.
AWS
SCP deny public S3/SG 0.0.0.0/0; centralized egress via TGW + firewall.
GCP
Org policy constrainPublicIp / disable public buckets; Cloud NAT at hub.
D5 · lz-segmentation · pair AP-D5
Segmentation by landing zone
Application landing zones are network segments, not names. Identity and network together define who can talk to whom.
  1. Does each application landing zone have a defined network segment and peering model?
  2. Are east-west rules explicit (allow-lists), not 'all spokes can talk'?
  3. Is production segmented from non-production on the wire, not only in a naming standard?
Azure
Spoke VNets per LZ; NSG/Azure Firewall policies; no prod-nonprod peering by default.
AWS
Account+VPC per LZ; SG/NACL + TGW route tables isolate prod.
GCP
Service projects + VPC-SC perimeters; Shared VPC subnet isolation.
Stream B · Anti-patterns
AP-D1 · per-app-internet-edge · pair D1
Per-application internet edge
Every team brings its own public IP, firewall flavour and VPN. The platform cannot see, inspect or retire paths.
  1. Do application teams create their own public IPs, firewalls or VPNs as the normal path?
  2. Is egress inspection optional per team?
  3. Is there no inventory of internet edges?
Azure
Public IPs on app VMs; app-level Azure Firewalls; no hub.
AWS
IGW on every VPC; no TGW; SG 0.0.0.0/0 common.
GCP
Public IPs on GCE; per-project Cloud NAT/VPN.
AP-D2 · flat-global-network · pair D2
Flat global network
Everything can route to everything. Segmentation is a slide. A compromised sandbox reaches production.
  1. Can every spoke route to every other spoke by default?
  2. Is production reachable from non-production on the network?
  3. Are NSG/SG/firewall rules effectively allow-any?
Azure
Full-mesh VNet peering; AllowVnetInbound NSGs.
AWS
TGW default route table associates all; 0.0.0.0/0 SG.
GCP
One big Shared VPC with default-allow and no VPC-SC.
AP-D3 · split-brain-dns · pair D3
Split-brain or absent private DNS
Each team runs DNS. Private endpoints do not resolve. Hybrid names work 'on my laptop'. Incident response cannot find things.
  1. Is private DNS missing, or different in every landing zone?
  2. Do private endpoints fail to resolve without tribal knowledge?
  3. Are hosts files and tribal resolvers in production use?
Azure

04Scoring against packs

How Phase 2 stays honest when clouds differ

Denominatorin-scope, applicable
Maturity depth and anti-pattern burden divide by criteria that are in Step 0 scope and not marked not-applicable. Out-of-scope GCP is not a silent 0.
Tested absenceanti-patterns only
An anti-pattern scores as clear only when the provider pack’s absence test ran (for example: no standing Global Admin assignments; no IAM user access keys on humans). Not looking is not clearance.
Control plane firstevidence class
Provider evidence objects are inventory, policy assignment, identity binding, log sink, IaC export. Workshop testimony can explain them. It cannot replace them for a GO on that criterion.
Pair registrycapability ↔ anti-pattern
A capability at 3 with its paired anti-pattern confirmed present is a contradiction. Phase 2 flags it. Phase 3 may not narrate excellence over a live anti-pattern.
05What this proposal is not yet

Preliminary — freeze after review

  1. Sub-criteria are the 3 questions — shared. Provider rows are evidence contracts, not a second questionnaire.
  2. Native-only extras (Azure Policy exemption objects, AWS RCP, GCP VPC-SC as a first-class criterion) can be added later as native rows. They should not fork the eight batches.
  3. Evidence category taxonomy for landing zone (Inventory / Identity-binding / Policy-assignment / Network-path / Log-sink / IaC / Workshop) still needs a locked enum.
  4. Golden fixtures per provider pack (Crawl / Walk / Run plus document-type and inventory-type) are required before scoring is production.
  5. Counts may move — 5+5 per batch matches the FinOps Engine shape for review. A later freeze might drop a weak pair or split a native row. Do not treat 80 as sacred.

Reuse the kernel: packets, pairs, gates, unknown-is-not-zero. Replace the domain pack. Describe every provider check in the Engine, or do not score it.
